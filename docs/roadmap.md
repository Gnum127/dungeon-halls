## Этап 3. Гексагональная сетка ✅ ЗАВЕРШЁН

Каждый пункт = одна сессия с чек-листом и двойным ревью. Порядок:
модель → математика → рендер → инструменты → UI.

Ключевые решения:
- **Параметризованный layout** (матрица ориентации Red Blob Games): одна
  формула для flat-top и pointy-top, ориентации как данные. Иерархии
  классов нет.
- **Оси**: канонические координаты модели остаются offset (`y*width+x`);
  axial используется только внутри hex-математики. В 3.2 фиксируются
  конверсии offset↔axial для каждой ориентации (odd-r / odd-q) и
  property-тест `pixelToCell(cellCenter(c)) === c` по всем клеткам.
- **cellSize для гекса** = радиус описанной окружности; границы канвы и
  PNG-экспорта считаются через geometry-bounds функцию, а не `w*cellSize`.

- [x] 3.1 Модель и миграция: `gridType: 'square' | 'hex-flat' | 'hex-pointy'`
      в MapModel и `createEmptyMap(width, height, gridType='square')`;
      `MAP_VERSION` 1→2; io принимает version ∈ {1,2} (v1 → gridType
      'square'), >2 и невалидный gridType → ошибка загрузки (MapLoadError —
      конвенция io); serializeMap пишет gridType; `replaceMap`: gridType в
      предикате no-op, поле опционально с дефолтом 'square' (генераторы
      отдают квадрат). Тесты: roundtrip v1/v2, миграция файла без gridType,
      смена только gridType меняет документ
- [x] 3.2 Hex-математика `src/shared/hex.ts`: параметризованная
      ориентация (матрица f²/b из Red Blob Games), pixelToCell (axial +
      cube-round), cellCenter, cellCorners; конверсии offset↔axial
      (odd-r для pointy, odd-q для flat — зафиксировать); property-тест
      round-trip по всем клеткам тестовой карты + known-answer точки
- [x] 3.3 Рендер и границы: renderMap рисует полигоны клеток по geometry
      (вместо прямоугольной ветки), culling видимости через hex-bounds,
      позиционирование объектов через cellCenter; strokePreview и
      cellHighlight переходят на polygon клетки; **pngExport переводится на
      geometry-bounds** (габариты гексов шире/выше w·cellSize — иначе экспорт
      молча обрезает края; лимиты пересчитываются от фактических границ);
      тесты fakeCtx (полигон клетки, смещения, отсечение, полнота покрытия
      крайних клеток в экспорте)
- [x] 3.4 Инструменты: useCellFromEvent/useHoverCell получают gridType в
      аргументах (сигнатуры меняются, потребители useTerrainBrush/
      useObjectTools наследуют hit-test автоматически); интеграционные
      тесты: клик красит гекс, drag-штрих по гексам, объект ставится в
      центр гекса
- [x] 3.5 UI и документ: выбор типа сетки — элемент управления уровня
      документа (панель инструментов), диспатчит НОВУЮ команду
      `setGridType` (метаданные: тайлы и объекты сохраняются, одна запись
      истории, no-op при неизменном типе). Генераторы пока поддерживают
      только `'square'`: при не-square сетке ОБЕ кнопки генерации
      («Сгенерировать» и «Ещё раз») задизейблены с подсказкой — покрыть
      RTL-тестом disabled-состояния (ограничение задокументировано в
      roadmap и README генератора). RTL-тесты, i18n ru/en
- [x] 3.6 Полировка: формат строки координат — чистая функция
      formatCoords(cell, gridType) (offset для квадрата, axial q/r для
      гексов) + unit-тесты; README по формулам и ориентациям

## Этап 4. Спрайтовая графика ✅ ЗАВЕРШЁН

Каждый пункт — размер одной сессии с самопроверкой по
`docs/quality-checklist.md` + вердикты PASS от `@reviewer` (код и тесты
отдельно). Порядок: каталог → манифест → загрузка → рендер тайлов →
рендер объектов + UI → экспорт → полировка.

Ключевые решения (зафиксировать до кода):
- **renderMap остаётся синхронной чистой функцией** `(ctx, model, viewport)`
  и НЕ знает про промисы. Спрайтовый режим добавляется опциональным
  аргументом-«атласом» `sprites?: SpriteRenderContext` — предзагруженный,
  иммутабельный снапшот готовых HTMLImageElement/BitmapImage; кто вызывает
  renderMap, тот и обеспечивает загрузку. Завершённая асинхронная загрузка
  триггерит перерисовку через React-состояние: хук `useSpriteAtlas`
  (useState) поднимается в EditorPage (composition root), т.к. атлас нужен
  и CanvasView для рендера, и MapFileActions для pngExport; туда он
  прокидывается props'ами. Атлас, приехавший после маунта, сам вызывает
  redraw за счёт смены state.
- **Режим отображения — настройка просмотра, а не данные карты**: в MapModel
  ничего не добавляется, MAP_VERSION не меняется, файлы проектов остаются
  совместимыми. Выбор «цвета / спрайты» хранится в localStorage ключом
  `dungeon-halls.editor.renderMode` (конвенция по образцу существующего
  `dungeon-halls.language`).
- **Ассеты — статика Vite**: `frontend/public/sprites/*.png`, пути в
  манифесте относительно base URL. Манифест — JSON с версией схемы;
  ЕДИНСТВЕННЫЙ источник путей — манифест (`Record<kindId, path>` для
  объектов, `Record<TileTypeName, path>` для тайлов); реестр объектов путей
  не содержит. Отсутствие файла манифеста вообще (404 при первом запуске до
  добавления ассетов) = валидный «пустой» атлас: приложение работает в
  цветном режиме без ошибок в консоли (fetch обрабатывается явно); любая
  ошибка валидации манифеста (битый JSON, неизвестные ключи, чужая version)
  ⇒ полный fallback на цвета, НЕ падение.
- **Каталог объектов — реестр данных вместо const-массива**:
  `{ id, labelKey(i18n), color }`; UI палитры объектов строится из реестра,
  новые виды добавляются записью данных + спрайтом в манифесте, без
  изменения логики.

- [x] 4.1 Каталог объектов: OBJECT_KINDS → реестр OBJECT_KIND_REGISTRY
      (данные: id, i18n-labelKey, цвет; БЕЗ путей к спрайтам); isKnownKind
      и OBJECT_COLORS выводятся из реестра (один источник правды); все
      потребители (палитра объектов, renderMap, тесты) переведены, публичное
      поведение не меняется. Unit/RTL-тесты зелёные без правок смысловых
      ассертов — иначе рефакторинг сломал контракт
- [x] 4.2 Типы и манифест спрайтов: `SpriteManifest { version, tiles:
      Record<TileTypeName, path>, objects: Record<kindId, path> }` (записи
      опциональны — нет записи = fallback на цвет); validateManifest:
      битый JSON / неизвестные ключи тайлов или kindId / неподдерживаемая
      version ⇒ результат «манифест невалиден» (вызывающий уходит в цветной
      режим), отсутствие записи ошибкой НЕ является. Манифест лежит рядом с
      ассетами (`public/sprites/manifest.json`), путь к нему — константа.
      Тесты валидации на чистых данных (без сети)
- [x] 4.3 Загрузчик и кэш: loadManifest(path) → Promise<SpriteManifest | null>
      (fetch по константе пути; null при 404/невалидном JSON) и
      loadSprites(manifest) → Promise<SpriteCache>;
      отсутствие файла манифеста (404) — нормальный путь: пустой атлас,
      без необработанных rejection; дедупликация параллельных запросов
      одного пути, отказ одного файла не валит весь пайплайн (этот спрайт
      просто отсутствует в атласе), провал не кэшируется навсегда (повторная
      загрузка возможна), таймаут загрузки. В jsdom Image мокается — тесты:
      404 манифеста → пустой атлас, дедупликация, частичный отказ, повтор
      после ошибки
- [x] 4.4 Спрайтовый рендер тайлов: опциональный аргумент renderMap
      (см. ключевые решения; пункт принимается по fakeCtx-тестам — UI-
      потребителя появится только в 4.5); отрисовка drawImage в клетку;
      clip по полигону клетки ТОЛЬКО для гексов (квадрат рисуется без clip —
      бюджет производительности), policy сглаживания зафиксировать
      (imageSmoothingEnabled: false — пиксель-арт при зуме остаётся чётким);
      culling как у цветного режима; fallback на цвет при отсутствии
      спрайта. FakeCtx-тесты: спрайт рисуется в центр клетки нужного
      размера, гекс-clip вызывается (и только для гексов), fallback работает
- [x] 4.5 Спрайтовый рендер объектов + переключатель режима: объекты рисуются
      спрайтом по kindId из манифеста (fallback — текущий кружок);
      хук useSpriteAtlas подключён в EditorPage, атлас прокидывается
      в CanvasView и MapFileActions (см. ключевые решения);
      UI-переключатель «цветные плитки / спрайты» (панель инструментов),
      выбор в localStorage `dungeon-halls.editor.renderMode`, состояние
      загрузки атласа (спиннер/ошибка) не блокирует цветной режим. RTL-тесты

- [x] 4.6 PNG-экспорт: экспорт использует тот же режим отображения, что и
      холст; РЕШЕНО: если атлас недоступен/не догрузился — экспорт цветами

- [x] 4.7 Полировка: README ассет-пайплайна (`editor/render/sprites/README.md`

## Этап 5. VTT-интеграция (стены, двери, свет) ✅ ЗАВЕРШЁН

Каждый пункт — размер одной сессии с самопроверкой по
`docs/quality-checklist.md` + вердикты PASS от `@reviewer` (код и тесты
отдельно). Порядок: модель → инструменты → рендер → свет → ZIP → сборка →
полировка. Зависимости: 5.1 → 5.2 → 5.3 → 5.4; 5.5 независимо от 5.2–5.4;
5.6 независимо от 5.1–5.5 (нужно только решение по зависимости);
5.7 требует 5.1–5.6.

> Решение по зависимости: автор согласился на `fflate` (контейнер ZIP,
> STORE). Новая зависимость добавляется в пункте 5.6.

Ключевые решения (зафиксировать до кода):
- **Стены и двери — отдельные сущности модели** (не тайлы): MAP_VERSION
  2→3, миграция ТРАНЗИТИВНАЯ v1→v2→v3 (io принимает version ∈ {1,2,3},
  пустые walls/doors при миграции), serializeMap пишет только текущую v3.
  `replaceMap` атомарно очищает objects+walls+doors (+lights с 5.5) —
  координаты теряют смысл на новой сетке; один undo возвращает всё;
  no-op-предикат команды расширяется на ВСЕ коллекции.
- **setGridType при непустых walls/doors/lights ЗАПРЕЩЁН**: команда
  возвращает модель без изменений, UI дизейблит выбор типа сетки
  с подсказкой (паттерн GeneratorPanel; квадратные рёбра бессмысленны
  на гексах). Очистка картой — через удаление инструментов, не молча.
- **Стена = ребро клетки**: `{ x, y, side: 'N'|'E'|'S'|'W' }`. Общие рёбра
  соседних клеток канонизируются (E клетки (x,y) ≡ W клетки (x+1,y),
  S ≡ N нижней) — нормализация в одном месте (model/walls.ts). ПЕРИМЕТР:
  E последней колонки и S последнего ряда хранятся КАК ЕСТЬ (соседа нет,
  канонизация только в сторону существующей клетки). Хранение — массив
  уникальных рёбер; сортировка/нормализация выполняются при КОММИТЕ
  команды, во время drag-штриха достаточно Set ключей (паттерн
  strokeKeysRef кисти).
- **Дверь принадлежит ребру**: `{ id, edge, open: boolean }` — одна дверь
  на ребро; позиция и ориентация производны от edge, не хранятся отдельно.
  Снятие стены (setWalls с present:false — тот же механизм, что у ластика),
  на которой стоит дверь, КАСКАДНО
  удаляет дверь той же командой (одна запись истории). Легаси-объект «door»
  из каталога объектов ОСТАЁТСЯ декоративным (клеточный спрайт/цвет);
  в portals .uvtt попадают ТОЛЬКО двери-рёбра — разграничение зафиксировать
  в README п.5.8.
- **Пакетная команда для штрихов**: setWalls(updates: {edge, present}) —
  одна запись истории на штрих, покрывает и рисование, и ластик (аналог
  setTiles кисти); одиночные toggleWall/addDoor — обёртки над ней.
  setDoors(…) в этапе не используется — задел на будущее,
  не реализовывать без потребителя.
- **Гексы вне MVP стен**: инструменты стен/дверей и UVTT-экспорт доступны
  ТОЛЬКО на square-сетке; на гексах задизейблены с подсказкой (i18n,
  RTL-тест disabled-состояния), ограничение задокументировано в README.
- **Свет — отдельная сущность**: `{ id, x, y, radius, color }` (radius в
  клетках, color hex). Рендер — полупрозрачный круг + маркер источника;
  физику освещения не считаем (это задача VTT-платформы). Выделение света —
  расширение select-инструмента (общий механизм выделения сущностей);
  повторный клик инструментом света по источнику удаляет его.
- **renderMap остаётся чистой функцией** того же контракта: стены/двери/свет
  рисуются поверх тайлов и объектов, в обоих режимах отображения.
- **Экспорт Universal VTT** (.uvtt): ZIP-архив (метод STORE — PNG уже сжат,
  сжатие не нужно) из `map.json` + PNG-рендер карты. **РЕШЕНО автором:**
  контейнер собирает зависимость `fflate` (`zipSync` с `level: 0`),
  самописный writer не делаем. `map.json`: resolution (map_origin 0,0,
  map_size в клетках, pixels_per_grid = 64 — согласован с PNG-экспортом),
  line_of_sight — замкнутые полигоны, собранные цепочкой из набора стен,
  portals из дверей-рёбер (bounds = концы ребра, closed = !open), lights из
  источников, environment с дефолтами. До сборки map.json сверить формат
  с эталонным .uvtt (пример Dungeondraft/DungeonFog — попросить автора или
  найти образец; поиск спецификации в сети был недоступен при планировании —
  формат зафиксирован по общеизвестной структуре, этап начинается со сверки).

  isEditableTarget уже есть; покрыть тестом по образцу сида генератора).

> 1. Свет в печати — ЧЕКБОКС: «Печатать источники света», по умолчанию

Ключевые решения (зафиксировать до кода):
- **SVG — всегда цветной векторный режим**: спрайты (растровые `<image>`
  по внешним путям) ломают автономность файла при печати; режим отображения
  пользователя игнорируется, как для UVTT-фона. Зафиксировать в README.
- **buildSvg — чистая функция** `(model) => string`: без DOM/Canvas,
  сериализация через массив строк; единица координат — константа
  SVG_UNITS_PER_CELL = 64 (толщины стен/дверей из renderMap остаются
  пропорциональными); square И все гексы поддерживаются сразу —
  в отличие от UVTT. Геометрия клеток: `traceCellPolygon` требует
  CanvasRenderingContext2D — сузить тип параметра до структурного
  `PathSink { moveTo, lineTo, closePath }` (renderMap использует только их),
  для SVG собирать список точек `<polygon>`; альтернатива — вынести чистую
  функцию «клетка → вершины полигона».
- **Порядок слоёв SVG = фактическому порядку renderMap**: фон → тайлы →
  линии сетки → объекты → стены → двери (сетка обязательна для печатной
  карты — GRID_LINE_COLOR из colors.ts). Стены/двери только на square
  (defense-in-depth guard как в renderMap). Единый источник цветов —
  `render/colors.ts` (не дублировать палитру в сериализаторе).
- **viewBox**: min-x/min-y покрывают отрицательные origin-сдвиги гексов
  (mapPixelBounds), width/height с Math.ceil как у PNG-холста; полигоны
  крайних гексов обязаны попадать внутрь viewBox (тест).
- **Числа в SVG**: фиксированный формат координат (константа округления) —
  float-координаты гексов (√3) иначе ломают детерминизм «байт в байт».
- **Тексты/шрифты в SVG не нужны** (подписей на карте нет) — шрифты не
  встраиваем, файл полностью автономен.
- **Свет в печати — опция пользователя**: чекбокс «Печатать источники
  света» (по умолчанию ВЫКЛ), ОДИН контрол для SVG и PDF. Флаг передаётся:
  в buildSvg вторым аргументом `{ includeLight }` (по умолчанию false);
  в renderToCanvas — опцией, прокидываемой в renderMap (на экране в canvas
  свет рисуется всегда, поведение по умолчанию не меняется). Тесты флага:
  unit в 6.1 (SVG), fakeCtx в 6.3 (PDF-рендер).
- **PDF печатает PNG-рендер страниц, ТОЛЬКО square-сетка**: гексовая
  разбивка по страницам не определена (клетки не целые); на гексах кнопка
  дизейблится с подсказкой (образец UVTT), гексы печатаются через SVG +
  браузерную печать. Векторный PDF НЕ делаем (двойная работа с
  SVG-сериализатором ради сомнительной выгоды для печати).
- **Страничный рендер**: сигнатура renderToCanvas расширяется прямоугольником
  страницы (viewport-сдвиг + клип); лимиты canvas считаются ОТ РАЗМЕРА
  СТРАНИЦЫ, не всей карты — снимает MAX_EXPORT_AREA для огромных карт.
- **Масштаб печати**: базовый стандарт D&D — клетка = 1 дюйм (5 футов);
  пользователь выбирает размер страницы (A4/A3/Letter), ориентацию и
  масштаб клетки (1"/0.5"); большая карта режется на страницы СЛЕВА
  НАПРАВО, СВЕРХУ ВНИЗ, клетки НЕ разрезаются (размер страницы округляется
  вниз до целого числа клеток; остаток — поля, контент прижимается к ЛЕВОМУ
  ВЕРХНЕМУ углу страницы).
- **Разрешение страниц PDF**: rasterScale ~150–200 px/клетку (64 px = 64 DPI
  — мыльные линии при печати 1"); лимиты canvas от размера страницы это
  позволяют.
- **Метаданные PDF**: Title — константа по образцу UVTT_MAP_NAME (поля name
  в MapModel НЕТ; добавлять его с миграцией MAP_VERSION ради печати не
  будем); страницы без сжатия сверх того, что даёт PNG.

## Этап 11. Комнаты: покрытие выбранным тайлом и новый многогранник

### 11.1 Заливка комнат выбранным покрытием (ластик = очистка)

- Модель: `model/rooms.ts` — `rectRoom` и `polygonRoom` принимают
  `tile: TileValue` вместо константы `FLOOR_TILE`; при `EMPTY_TILE` команда
  очищает тайлы области и НЕ добавляет стены (тест на это).
  `FLOOR_TILE` из сигнатур убирается.
- Совместимость: миграция файлов v4 НЕ нужна — тайлы хранятся числовыми
  индексами, загрузка комнат, залитых `floor`, меняется только в том смысле,
  что для новых комнат тайл приходит параметром. Зафиксировать roundtrip-тест
  «сохранить → загрузить» на существующем v4-файле с комнатами.
- Поток: `EditorPage` держит `brushTile` в state — единый источник для кисти
  и комнат; прокидывается в `CanvasView` → `useRectRoomTool` /
  `usePolygonRoomTool` → `commitRoom`. `lastBrushTileRef` остаётся ref
  (значение не влияет на рендер, горячие клавиши B/E восстанавливают кисть
  из ref, как сейчас).
- UI: в панели «Комнаты и стены» (`RoomTools`) — маленький свотч текущего
  покрытия (цвет из `TILE_COLORS` + имя из i18n), чтобы было видно, чем
  зальётся комната; при ластике — подпись «очистит область».
- Команда `addRoom` не меняется (tiles+walls одной записью истории; ластик
  даёт tiles с EMPTY и walls=[] — no-op-логика уже на месте).

### 11.2 Новый многогранник «центр + радиусная точка» (замена кликов)

- Панель `RoomTools`: числовое поле «вершин» (min 3, max 12, шаг 1,
  `MAX_POLYGON_VERTICES = 12`); значение — prop в `CanvasView`.
- Хук `usePolygonRoomTool` переписывается: состояния `idle → placingCenter
  → placingRadius(превью) → commit`. Первый клик — центр; курсор сдвигает
  вторую точку; клик №2 — фиксирует первую вершину и радиус; остальные
  N−1 вершин строятся по окружности; `Esc` отменяет начало.
  Второй клик в ту же клетку, что и центр, не коммитит (радиус=0).
- Чистая функция `model/rooms.ts`:
  `regularPolygonVertices(center, radial, count, width, height)`:
  направление первой вершины — от центра к радиальной точке (задаёт поворот),
  углы `k·2π/count`, точки `center + r·(cos,sin)`, округление к центрам клеток,
  клампинг в границы карты. ПОВЕДЕНИЕ ОБЯЗАТЕЛЬНОЕ:
  (а) dedup ДО возврата — функция возвращает вершины без дублей вообще
  (снятие глобальных, не только consecutive, совпадений); `polygonRoom`
  не трогаем (его consecutive-dedup остаётся страховкой для других путей);
  (б) после dedup осталось <3 вершин — функция возвращает пустой массив,
  инструмент не коммитит (пустая комната, без ошибки);
  (в) клампинг применяется только к координатам вершин (углы фиксированы) —
  при зажатой у края карты вершине полигон может стать нерегулярным, это
  осознанное поведение, зафиксировать тестом на «неравные стороны после
  clamp».
- Превью: `render/roomPreview.ts` уже рисует заливку/стены/вершины — рисуем
  готовый полигон в реальном времени; при „placingCenter“ — только точка.
- Старый по-кликовый ввод вершин полностью удаляется (тесты переписываются).

### 11.3 Тесты

## Этап 13. Изображения элементов (готовый набор в проекте)

Пользователь работает с готовым набором изображений из проекта (не загрузка
файлов). Привязка «вид объекта → изображение» глобальная (на всех картах),
действует через данные проекта + персист выбора в localStorage.

### 13.1 Набор изображений и дефолты

- Ресурсы в проекте: `public/element-images/` + манифест
  `element-images/manifest.json`: `{ version: 1, items: { <imageId>: path } }`
  — пул готовых картинок (валидация в стиле `sprites/manifest.ts`).
  `imageId` — глобально уникальный стабильный slug (строка, независимая от
  kindId, например `table-wooden`); на один вид может приходиться несколько
  картинок пула (для пикера). Инвариант: `defaultImage` вида обязан ссылаться
  на существующий `imageId` пула; при нарушении/отсутствии картинки — fallback
  на цвет, без лога ошибки (как в sprites-пайплайне).
- `model/objects.ts`: у `ObjectKindEntry` поле `defaultImage?: string`
  (imageId из пула) — изображение вида по умолчанию.
- Загрузка: расширяем `render/sprites/loader.ts`/`manifest.ts` вторым
  манифестом и группой `elementImages: Partial<Record<ObjectKindId, HTMLImageElement>>`
  в `SpriteAtlas`; переиспользуем `requestImage`/`resolveSpriteUrl`
  (дедупликация, таймаут, отказ одного файла = fallback).

### 13.2 Выбор изображения для вида

- `ObjectPalette.tsx`: у активного вида — пикер миниатюр из пула
  (сетка/дропдаун), включая пункт «по умолчанию».
- Выбор персистится в localStorage (`dungeon-halls.editor.elementImages.<kindId>`,
  префиксная конвенция). Хук `usePersistentElementImage(kindId)` реализуется по
  паттерну `safeStorage()` (try/catch на чтение/запись, quota/приватный режим →
  молчаливый fallback на дефолт), как `loadRenderMode`/`saveRenderMode`.

### 13.3 Рендер и экспорт

- `renderMap.ts`: для объекта приоритет изображения —
  override(localStorage) → `defaultImage` → спрайт-ассет → цветной свотч
  (эллипс как сейчас). Рисуется `drawImage`, растянутым на footprint
  (`w = baseSize·scale.w`, `h = baseSize·scale.h`), с поворотом вокруг
  центра footprint — существующая ветка sprite-рендера объекта.
- PNG-экспорт: `SpriteRenderContext` расширяется группой `elementImages`,
  `exportMapToPng`/`vtt` используют общий атлас (картинки попадают в PNG).
- SVG/PDF остаются векторными (цветные формы): `buildSvg` и PDF-рендер
  НЕ принимают атлас — канал для изображений отсутствует структурно
  (инъекции нет). Зафиксировать тестом: SVG-вывод не содержит `<image>`
  даже при подставленном атласе с elementImages.

### 13.4 Тесты

- Валидация второго манифеста (битый JSON/неизвестный imageId/version).
- Pull-загрузка пула: дедупликация, таймаут, отказ файла → fallback на цвет.
- Персист выбора + приоритет override > default.
- Рендер: drawImage растянут с поворотом (fake-ctx), fallback при отсутствии.
- PNG-экспорт включает изображения.
